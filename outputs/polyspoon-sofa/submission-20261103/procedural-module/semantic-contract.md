# Semantic contract v1

Canonical `buildAsset` returns `SemanticAssetBuild`. Its `semantics` field and `root.userData.openpoly` contain the same plain JSON. Procedural modules create this metadata through the same adapter. The module's frozen `metadata.semantics` describes its family default; inspect a created root for the selected variant and runtime pose. GLB export retains the contract and per-mesh semantic references in glTF extras. Semantic exports include the complete authored asset regardless of preview visibility; hidden meshes/groups remain in the exported mapping. Raw nonsemantic preview export keeps its existing visibility behavior.

`identity` records family and recipe version. `coordinates` declares meters, +Y up, +Z front and the existing ground-center origin. The ground-center origin is the authored primary-body ground reference, not a recomputed bounding-box center. Anchor coordinates are authored points relative to the asset root, in meters. They describe the constructed design and do not automatically track runtime poses.

`controls` includes `inputUnit` and `displayUnit`, generated by the shared `controlMetadata` function. Legacy `Control.unit` remains the display convention. A centimeter slider still takes meter values; a ratio is dimensionless; counts and seeds are integers. Chest `lidAngle` takes degrees. No control names, bounds or input values were rescaled.

`parts` maps stable semantic IDs to authored node names, semantic material-role IDs, actual delivery material names and motion groups. Existing mesh names are preserved. IDs refer only to parts present in this variant: removing a latch or changing wheel construction can remove IDs. Wheelbarrow strap IDs use side/course identity rather than a length-dependent coordinate in their existing display names. `materials` identifies semantic roles; appearance may create several actual materials for a role.

Each mesh carries `userData.openpoly` with `partId`, `materialId` and group. Prefer these IDs when a target loader sanitizes node names. For example, Three's glTF loader may replace a period in an authored node name. The source delivery name remains in `parts.node`; the per-node semantic ID survives import.

## Declared runtime joints

`joints` is empty for static families and for variants without the declared moving assembly. Every declared joint is a revolute group, with a root-relative pivot, unit axis, degree range and current angle. Joint node names must match `[A-Za-z][A-Za-z0-9_-]*`, for example `wheel_pivot`. Names such as `wheel.pivot` or `wheel:pivot` reject at declaration because glTF loaders may sanitize them. Semantic part IDs and authored mesh names retain their wider character set; per-mesh IDs handle their documented loader-name changes.

| Family | Group | Authored pivot and axis | Supported degrees | Moving parts |
|---|---|---|---|---|
| Wheelbarrow | `wheel-axle` | Existing wheel center `[0, wheelRadius, trayLength/2 + 0.16]`, +X | -180 to 180 | Tread, wood disks/braces or rim/spokes/hub |
| Treasure chest | `lid-pivot` | Rear hinge `[0, bodyHeight, -depth/2]`, -X | 0 to 110 | Lid, lid bands, latch and keyhole |
| Stone well | `windlass-pivot` | Existing axle `[0, wallHeight + 0.95, 0]`, +X | -180 to 180 | Windlass, spool flanges and crank arm/grip |

Wheelbarrow axle/handles and well bearings/posts stay fixed. Well rope, bucket and supports remain independent of the rigid windlass pose. This API provides rigid articulation; it does not supply rope simulation, physics, IK, animation clips or automatic winding.

```ts
import { buildAsset } from './src/catalog/index.ts';
import { setJointPose } from './src/catalog/semantics.ts';

const build = buildAsset('treasure-chest', { lidAngle: 20 });
setJointPose(build.root, 'lid-pivot', 70);
```

A packaged procedural module also exports `setJointPose(root, jointId, degrees)`. Poses set an absolute angle, rather than adding to the current angle. The operation updates the declared joint angle and node transform. It preserves saved procedural parameters. The chest's `lidAngle` parameter establishes its initial pose; a later runtime pose does not rewrite that saved parameter. Save runtime poses separately if an application needs them. Bounds/dimensions on a build describe construction; recompute a Box3 from the root after runtime posing when needed.

## Delivery boundary

The editable hierarchy remains authoritative. Version1 delivery uses one mesh node per semantic part and separate moving groups. Static batching is not implemented. A future delivery adapter must retain a source-part mapping into merged geometry ranges, preserve semantic material-role mapping and keep different moving groups separate. It must never replace the editable semantic asset or silently discard IDs.

The well's many stationary masonry meshes offer a concrete later batching opportunity: group compatible fixed masonry by material while retaining each source-part range. Keep windlass meshes and independently posed assemblies outside that batch. Measurements and representative renders belong with the exact recipe version and parameters.

## Historical grouping release (R11)

The R11 joint-grouping release preserved its then-current recipe versions and saved-design loading. Geometry attributes and indices remained identical across its retained changed-recipe cases. Reparenting introduced at most normal floating-point translation error in world matrices; that release's evidence records its bound. Existing mesh/material names and authored colors were unchanged in that grouping change.

That historical result does not describe the later construction revisions. Current recipe versions, geometry changes, strict supported migrations and per-part color behavior are documented in [construction migration](../construction-migration.md).
